# Moonshot community · local implementation

## Integration

- Student: `CommunityPanel({ snapshot, demo, onOpen, onRewards })` from `panel.tsx`; callbacks are optional.
- Moderator: `CommunityModerationPanel({ cohortId })` from `moderation-panel.tsx`.
- `GET /api/campus/community?enrollmentId=<uuid>&view=all|mine|feedback|talent|demo_day&page=0` reads 30 posts at a time. `POST` accepts validated commands.
- `GET /api/campus/community/moderation?cohortId=<uuid>` / `POST` requires current `members` operator permission.
- `GET /api/campus/community/rewards?enrollmentId=<uuid>` returns the current authenticated learner's verified reward state for the spatial renderer. `campus:community-changed` is a refetch signal in live mode; do not trust its client payload as evidence. The separate in-memory demo cache in `events.ts` is synthetic and resets on page reload.
- All community routes require `EDU_CAMPUS_ENABLED=true` and `EDU_CAMPUS_COMMUNITY_ENABLED=true`.
- New SQL: `20261102151403_edu_campus_community_workflows.sql` and `20261102225053_edu_campus_community_exchange_demo_files.sql`. Neither has been applied to DEV or production by this implementation. The existing mission permission migration `20260922054307_mission_priority_integrity.sql` is a prerequisite; missing `private.mission_has_scope(text)` must stop rollout, not grant fallback access.
- `requestCommunityOpen({ enrollmentId, tab: "demo_day" | "all", postId?, sessionId? })` stores a one-time in-memory intent until the matching community panel mounts. The space button uses it before navigation. `/api/campus/community/demo-session?enrollmentId=<uuid>` reads at most the current cohort's visible presenting session; the event is navigation only and never a permission proof. A targeted post beyond the first page uses the same authenticated/RLS read checks. Older in-flight responses cannot replace a newer selected view.
- `GET /api/campus/community/exhibition?enrollmentId=<uuid>` returns up to six explicitly cohort-shared portfolio titles/aliases and version metadata from the most recent 24 candidates. The current learner/course/cohort must remain active. Ordinary user RLS checks sharing, hidden status and bilateral blocks; a server-only check excludes open reports and then rechecks current authorized posts before returning. No body, URL, image or iframe is exposed on the space monitor. `getCommunityDemoExhibition(enrollmentId)` returns only synthetic in-memory shared work; demo state survives host-tab navigation and resets on page reload.

## Implemented

Private portfolio / cohort feedback requests / public-to-cohort process and failure records / talent offers and requests / demo-day submissions use typed posts. Each edit appends an immutable version and a change note. Former private revisions do not become visible when a later version is shared. Switching the current post back to private removes peers' history access.

Comments bind to the version seen. Only the recipient can record usefulness, application to a newer saved version, or a reason to keep the existing version. One recipient counts once toward the author's helpful contribution. Self-acknowledgment, stale revisions, repetitive comments, and replayed mutations are rejected. Writes and idempotency receipts commit atomically.

XP, badges and individual eligibility are calculated from the existing latest approved required mission submissions, distinct useful-feedback recipients, and evidence of a newer version incorporating feedback. Timers, presence, subjective business results, or client-provided XP do not affect eligibility. `moonshot-v1` gives 100 XP/approved required mission, 20 XP/distinct useful-feedback recipient, one level/200 XP; launch requires at least one required mission and all required missions approved, one useful-feedback recipient and one applied revision. Five unique historical launches count toward the cohort rocket. Launch proof stores the rule version and source IDs/revisions; it is historical proof, not an immutable claim that future curriculum is completed.

Reports are private to reporter and authorized operators. Blocking is bilateral for content access and reversible. Operators can inspect shared or reported posts, not unrelated private portfolios. Hide/restore/resolve actions require a reason and append an audit row. Normal users cannot directly mutate tables, reward rules, evidence or audit records; a narrow private RPC checks current actor/scope and performs writes. Public wrappers are security invoker; RLS protects every direct read.

## Limits and verification

- Demo is synthetic, memory-only, labeled, and uses real command validation plus ownership/CAS transitions. It never calls the live API.
- Screenshot/PDF attachments accept PNG/JPEG/WebP/PDF up to 10 MB with server-issued paths, signed non-upsert uploads and server size/MIME/signature/hash verification. Files bind to the saved portfolio version and start private. Each file requires a separate owner confirmation to share with the current active cohort; sharing a post never automatically shares old files. Reads recheck current post visibility, active owner/reader enrollment, bilateral blocks and open reports. Switching a post to private or hiding it revokes its file shares; republishing does not restore them. New download links stop after revocation, while an already-issued signed URL lasts at most 30 seconds and downloaded copies cannot be recalled.
- Talent exchange includes an explicit proposal → recipient accept/decline → proposer result submission → recipient completion confirmation, cancellation before acceptance, participant-only history and CAS/idempotence. Neither party can approve its own side. There is no automated matchmaking, dispute resolution, fee or financial settlement.
- Demo day includes cohort-conflict-checked 5–30 minute slots, presenter cancellation, operator start/finish, audience questions and presenter answers. The moderation panel exposes operator controls. The space feedback-lab/lounge can open the matching demo-day post and host controls through the durable navigation intent. There is no video/voice streaming, external invitation, automated notice or animated 3D presenter staging.
- External customer test rooms are owned by the business module, not this module.
- The initial reward rule is versioned and immutable; no operator rule-editing UI is shipped here.
- Post lists are paginated. Per-page history/comments and operator records have bounded limits and fail visibly if truncated rather than claim complete metrics.
- Local domain/API validation + PGlite PostgreSQL RLS/atomic workflow tests and desktop/mobile browser flows are implemented. Actual shared DEV, production auth/permissions, storage and load testing remain separate rollout checks.

Local verification: 29 domain/API/PGlite tests and 20 desktop/mobile community browser scenarios passed; the shared run also passed 4 office browser scenarios. The space owner separately passed 2 desktop/mobile space-to-demo-day navigation checks. Exhibition endpoint tests cover withheld reports, stale shares, scope loss, metadata-only output and strict auth/flags; browser tests verify that a late former-view response cannot overwrite the current portfolio. Run `node --test tests/campus-community*.test.mjs` and `CAMPUS_QA_PORT=4505 npx playwright test --config=playwright.campus.config.ts tests/campus-browser/community.spec.ts --output=test-results/campus-community-extension`.

## Exchange / demo day / attachment extension

Migration `20261102225053_edu_campus_community_exchange_demo_files.sql` adds the state transitions and private file metadata/bucket. It depends on the original community migration and the normal Supabase Storage schema. It is **local only**, not applied remotely. Mismatched existing bucket settings cause a stop rather than silently change them. The new bucket is private; restrictive read/update/delete policies prevent unrelated permissive Storage policies from opening or replacing its files. Signed uploads are append-only. RLS protects file metadata, exchange participants and cohort demo events; user-facing endpoints are:

- `/api/campus/community/workflows`: current selected post's exchanges, cohort schedule, questions/history and atomic commands. Every mutation checks current post visibility, membership/operator permissions, actor, revision and idempotency receipt.
- `/api/campus/community/files`: RLS-filtered list, owner prepare/verify completion, explicit file-share CAS and protected download. Binary data goes directly to a server-issued signed Storage URL; normal EDU API requests are bounded metadata JSON. No user-supplied path or owner is trusted. Download rechecks permissions and redirects to a 30-second Storage URL with attachment disposition; the redirect uses no-store, nosniff and no-referrer. The separate owner-only share log preserves changes. Anonymous users and unrelated cohorts cannot obtain metadata or fresh links.

The file contract limits each portfolio to 20 files and each owner to 50 reservations/day; there is no automatic orphan cleanup or malware scanning. Invalid/incomplete uploads remain pending and are never served as ready files. Cleanup/retention and a real DEV Storage/CORS/signed-token exercise are rollout work. Unsaved form/file-share confirmation drafts register with the campus navigation guard; empty and unchanged forms do not block leaving, and successful saves clear the guard. The local browser fixture validates actual selected/dropped/pasted bytes in memory; mocked API tests verify completion and unauthorized access; PGlite executes actual RLS and state transitions. These tests do not claim a real external upload succeeded.

## Safe rollout / rollback

Keep both gates off until the migration and authenticated DEV verification succeed. Existing EDU lessons/submissions are read-only inputs. No class completion, payment, notification, real student answer or profile name is changed. On rollback disable the gate and retain all new tables/evidence; do not drop data after users have saved work. No supplied 3D ZIP has been edited.
