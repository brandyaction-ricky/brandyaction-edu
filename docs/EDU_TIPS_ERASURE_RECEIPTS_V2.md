# EDU TIPS v2 삭제 진행 회신·연속 ACK — DB 처리 기반

1단계 삭제 요청 보관 SQL 위의 후속 구현이다. 공개 HTTP API·실제 DB 적용·원격 삭제 실행은 포함하지 않는다.

## 구현한 것

- 운영/DEV·조직·브랜드에 묶인 별도 소비자 설정과 요청별 발행 원장. 소비자 설정은 초기 값이 없고 서버 역할도 생성/변경할 수 없다. 실제 등록은 별도 검수·승인 범위다.
- 발행 시 소비자 행을 먼저 잠근 뒤 이미 commit된 삭제 요청만 읽고 순번을 부여한다. 다음 발행은 앞 발행의 commit 후 진행한다. 생성 시각이나 원천 sequence를 읽기 완료 기준으로 사용하지 않아, 뒤늦게 등장한 오래된 요청도 뒤 순번으로 발행한다.
- 회신에는 엄격한 허용 필드·자료형·가명 ID·단계·누적 삭제수·증거 해시·UTC 시각 검사를 적용한다. 알 수 없는 요청, 다른 회원/세대, 미발행 소비자, 미래·역순 시각, 완료 단계의 미처리 모델/잔존 자료를 거절한다.
- 동일 receipt ID·동일 JSON은 원래 접수 결과를 반환한다. 다른 내용은 충돌이다. 이후 회신은 revision 증가·단계 비후퇴·누적수 비감소를 요구하며 이미 기록한 완료 시각과 처리 결과를 바꾸지 못한다.
- ACK는 발행된 내부 delivery ID를 지정한다. 1완료/2대기/3완료에서는 1까지만 가능하며, 이전 ACK 재시도는 최신 ACK를 반환한다. 다른 소비자나 미발행 ID, 누락 순번은 거절한다.
- 기한을 넘긴 회신도 접수하지만 위반 표시는 유지한다. receipt 기록은 서버 역할도 수정·삭제할 수 없다.

## 완료라는 말의 경계

`erasure_deliveries.completed_at`은 **해당 소비자가 계약 형식에 맞게 완료를 보고했다**는 뜻이다. 증거 해시만으로 실제 모델·백업 삭제를 검증했다고 볼 수 없다.

전역 `erasure_outbox.completed_at`은 이번 코드도 쓰지 않는다. 모든 실제 수신자의 삭제·최종 ACK를 확인하고 새 분석을 재개하는 정책 연결은 후속 단계다. 현재는 계속 재등록을 막으므로 보고만으로 분석을 다시 시작하지 않는다.

## 공개 API 연결 전 남은 것

1. API 전용 키의 환경/소비자/scope 확인, 제한·회수와 응답 스키마 검사. DB 함수는 인증된 서버만 호출하며 요청 본문에서 소비자 ID를 신뢰하면 안 된다.
2. 내부 delivery UUID/순번은 공개 cursor가 아니다. 소비자·환경·브랜드·스트림·기한에 묶인 서명 cursor 발급/확인과 ID 대응을 HTTP 계층에서 구현해야 한다. 이번 RPC 반환을 그대로 고객 또는 TIPS 공개 API로 내보내지 않는다.
3. 중지 통지 수신 규격, 실제 TIPS 워커·모델·백업 검수 및 모든 수신자 ACK 후 분석 재개 정책.
4. 회신이 전혀 오지 않는 기한 초과를 감지하는 운영 경보. 현재 위반 표시는 회신 접수 시 계산한다.
5. 실제 DEV 다중 연결 경쟁 시험. PGlite의 순차 late-arrival·rollback·멱등 시험은 다중 트랜잭션 검수의 대체가 아니다.

초기 데이터, 키, 예약 실행, 기능 플래그를 추가하지 않는다. DEV·운영에 적용하지 않았으며 1단계·이 SQL의 실제 적용은 승인 후 별도 진행한다.
