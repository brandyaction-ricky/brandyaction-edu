# EDU TIPS 삭제 기한 확인 — 회신 없는 요청 포함

상태: 선행 삭제 원장·회신·기한 SQL은 승인받은 DEV DB에 적용했고 격리 Preview에서 가상 데이터로 검수했다(2026-10-10). 이번 변경은 내부 상태 검사 코드이며, 예약 실행·고객/담당자 알림 발송·운영 활성화는 아직 없다.

## 달라진 점

기존 receipt 접수 때의 위반 표시만으로는 TIPS가 아무 회신도 하지 않는 요청을 찾지 못한다. `edu_tips_check_erasure_deadlines(consumer_id, limit)`는 소비자별 발행 전 요청까지 확인한다. 최초 요청에 저장된 활성5일·모델30일·잔존30일 기한을 사용하며 기한을 다시 계산하거나 늘리지 않는다.

- 회신 없는 요청, 활성 삭제만 보고한 요청, 모델/백업 대기, 늦게 완료한 요청을 구분한다.
- 기한 초과 관측은 요청·소비자·단계별 최초 시각과 당시 기한을 별도 원장에 보존한다. 반복 확인은 중복 원장을 만들지 않는다.
- 나중에 ‘기한 안에 삭제했다’는 회신을 받아도 이전의 증거 미도착 이력은 지우지 않는다. 이 관측은 증거가 늦었다는 뜻이며, 실제 삭제가 늦었다는 사실과 구분한다.
- 화면용 최대200건 제한과 전체 집계가 분리돼 있어 목록이 잘려도 전체 지연 건수를 알 수 있다. `truncated`를 확인한다.
- 소비자가 없으면 오류다. 다른 소비자의 완료 회신으로 미응답을 해소하지 않는다.
- 완료 보고 후 ACK 대기와 전역 검증 대기를 별도 표시한다. 이 함수는 삭제 완료·ACK·분석 재개를 수행하지 않는다.

## 권한·응답

이 함수는 service_role 전용 내부 작업이다. 소비자 확인부터 시작하고 기존 발행·receipt·ACK와 같은 잠금 순서를 사용한다. 공개 API나 브라우저에서 호출하지 않는다.

응답에 회원 UUID·customer_id·consent_epoch·receipt 원문·연락처를 포함하지 않는다. 내부 request_id·delivery_id·consumer_id와 단계/기한만 포함하며, 그대로 TIPS 외부 응답에 쓰면 안 된다. 새 감사 원장은 서비스 역할에도 수정·삭제를 허용하지 않는다.

## 남은 연결

- 이 함수는 호출될 때만 확인한다. 아래 내부 상태 검사 경로를 준비했으며 예약 실행·관리자 경보 화면/메시지는 아직 연결하지 않았다.
- 신규 분석 차단과 TIPS 원격 작업 취소는 기존 철회 경로 및 후속 즉시 제어 구현의 책임이다. 이 함수를 추가했다고 원격 처리가 중지됐다고 주장하지 않는다.
- 새 소비자 등록 때 어떤 과거 요청을 처리해야 하는지, 실제 수신 대상 범위는 공동 검수에서 확정한다. 현재 발행 함수와 같게 등록 소비자별 모든 삭제 원장을 확인한다.
- 선행 DEV 검수에서 다중 연결·철회와 등록 경합·늦은 커밋을 확인했다. 이번 상태 검사의 실행 시간·큰 원장 성능·TIPS 실제 원격 삭제·모델·백업 검수는 남아 있다. 로컬 PGlite 시험은 운영 검수의 대체 증거가 아니다.

## 내부 상태 검사 연결

`GET /api/cron/tips-erasure-deadlines`는 `Authorization: Bearer <CRON_SECRET>`으로만 호출한다. 브라우저에 이 비밀값을 주거나 TIPS 수집 키로 호출하지 않는다. 응답은 항상 `no-store`다. HEAD는 405로 거절하며 관측 원장을 쓰지 않는다. URL 인자로 소비자·환경·범위를 바꿀 수 없다.

필요 설정은 서버의 `EDU_TIPS_ERASURE_MONITOR_ENABLED=true`, `EDU_TIPS_ERASURE_MONITOR_CONSUMERS`(쉼표로 구분한 소비자 UUID 1–8개), 기존 `NEXT_PUBLIC_APP_ENV`(`development` 또는 `production`)다. 기본 꺼짐이며 빈 목록·중복·알 수 없는 환경은 점검 성공으로 처리하지 않는다. 기존 내보내기/삭제 API의 켜기 스위치와 독립적이라 전송을 끈 상태에서도 삭제 기한을 확인할 수 있다.

이 경로는 DB에서 **최초 기한 초과 관측을 기록할 수 있다**. 읽기만 하는 health check가 아니다. 각 소비자별 전체 원장의 집계를 사용하며 상세 목록은 1건만 요청하고 응답에서 폐기한다. 회원·요청·소비자 ID, 회신 원문, DB 오류는 HTTP 응답에 넣지 않는다. 환경 또는 소비자가 다르게 돌아와도 503으로 실패한다. 호출 전 승인받은 프로젝트와 소비자 목록을 확인해야 하며, 응답 환경 검사는 잘못된 DB 연결 자체를 막는 장치는 아니다.

| 결과 | 의미와 후속 처리 |
|---|---|
| 200 `overdue`, `checked=true` | 전 대상 검사 완료, 기한이 지났는데 단계별 증거가 없는 요청 존재. 담당자가 확인할 경보 조건 |
| 200 `no_overdue`, `checked=true` | 현재 기한 초과 없음. 물리 삭제 완료 또는 분석 재개 허가가 아님 |
| 503 `disabled` / `configuration_required` | 점검 꺼짐 또는 설정 누락. 정상 점검으로 기록하면 안 됨 |
| 503 `check_unavailable` | DB 오류·잘못된 집계·환경 불일치·10초 시간 초과. 일부 성공 집계도 반환하지 않음 |
| 401 / 400 / 405 | 인증 실패 / 범위 변경 시도 등 URL 인자 / 지원하지 않는 메서드 |

`signals`는 회신 없음, ACK 대기, 전역 검증 대기, 과거 위반 이력을 별도 표시한다. 회신 없음은 기한 전에도 참일 수 있어 곧바로 기한 초과로 해석하지 않는다. 과거 위반 이력은 늦게 완료해도 남으며 현재 지연과 구분한다. `summary`의 건수는 **소비자–요청 쌍**이다. 여러 소비자가 같은 요청을 처리하면 각각 센다. 회원 수 또는 유일한 요청 수로 표시하지 않는다. `checked_from`–`checked_until`은 소비자별 DB 관측 시각 범위이며 여러 소비자의 전역 단일 트랜잭션을 뜻하지 않는다.

## 활성화 전 검수와 중단

1. 선행 네 SQL과 삭제 회신 API 검수를 보존하고 환경별 소비자 목록을 확정한다. 운영 소비자를 DEV 설정에 넣지 않는다.
2. 승인받은 격리 DEV에서 가상 요청으로 정상·미응답·5일 초과·30일 초과·늦은 회신·ACK·점검 실패를 확인한다. 현재 코드는 로컬 검수 단계이며 이번 변경으로 DEV 설정은 바꾸지 않았다.
3. 스케줄과 담당자 수신 경로를 정하고 별도 승인 후 연결한다. `vercel.json`의 cron 목록에는 이 경로를 추가하지 않았다. 실제 알림 수신, 점검 실패 알림, **예정 시각에 호출 자체가 없었던 경우**까지 검수해야 한다. 이 API만으로 호출 중단을 감지하지는 못한다.
4. 문제 시 `EDU_TIPS_ERASURE_MONITOR_ENABLED=false`로 끄고 호출을 중단한다. 이미 남은 관측·회신·원장·기한은 보존한다. HTTP 실패/중단이 이미 완료된 관측 트랜잭션까지 되돌리지는 않는다.

## 반영과 복구

기한 SQL은 선행 outbox/receipt SQL 이후 적용한다. 이번 코드에는 새 migration·초기 데이터·cron·설정 적용이 없다. 운영 DB 적용은 별도 승인 후 한다. 문제 시 호출을 중지하며 원장과 기한을 보존한다. 삭제·기한 연장으로 되돌리지 않는다.
