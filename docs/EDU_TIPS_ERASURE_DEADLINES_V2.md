# EDU TIPS 삭제 기한 확인 — 회신 없는 요청 포함

상태: 로컬 SQL 후보·합성 검수. 공유 DEV·운영 DB·예약 실행·고객/담당자 알림 발송은 변경하지 않는다.

## 달라진 점

기존 receipt 접수 때의 위반 표시만으로는 TIPS가 아무 회신도 하지 않는 요청을 찾지 못한다. `edu_tips_check_erasure_deadlines(consumer_id, limit)`는 소비자별 발행 전 요청까지 확인한다. 최초 요청에 저장된 활성5일·모델30일·잔존30일 기한을 사용하며 기한을 다시 계산하거나 늘리지 않는다.

- 회신 없는 요청, 활성 삭제만 보고한 요청, 모델/백업 대기, 늦게 완료한 요청을 구분한다.
- 기한 초과 관측은 요청·소비자·단계별 최초 시각과 당시 기한을 별도 원장에 보존한다. 반복 확인은 중복 원장을 만들지 않는다.
- 나중에 ‘기한 안에 삭제했다’는 회신을 받아도 이전의 증거 미도착 이력은 지우지 않는다. 이 관측은 증거가 늦었다는 뜻이며, 실제 삭제가 늦었다는 사실과 구분한다.
- 화면용 최대200건 제한과 전체 집계가 분리돼 있어 목록이 잘려도 전체 지연 건수를 알 수 있다. `truncated`를 확인한다.
- 소비자가 없으면 오류다. 다른 소비자의 완료 회신으로 미응답을 해소하지 않는다.
- 완료 보고 후 ACK 대기와 전역 검증 대기를 별도 표시한다. 이 함수는 삭제 완료·ACK·분석 재개를 수행하지 않는다.

## 권한·응답

이 함수는 service_role 전용 내부 작업이다. 소비자 확인부터 시작하고 기존 발행·receipt·ACK와 같은 잠금 순서를 사용한다. 공개 API나 브라우저에서 호출하지 않는다.

응답에 회원 UUID·customer_id·consent_epoch·receipt 원문·연락처를 포함하지 않는다. 내부 request_id·delivery_id·consumer_id와 단계/기한만 포함하며, 그대로 TIPS 외부 응답에 쓰면 안 된다. 새 감사 원장은 서비스 역할에도 수정·삭제를 허용하지 않는다.

## 남은 연결

- 이 함수는 호출될 때만 확인한다. 예약 실행·관리자 경보 화면/메시지는 아직 연결하지 않았다.
- 신규 분석 차단과 TIPS 원격 작업 취소는 기존 철회 경로 및 후속 즉시 제어 구현의 책임이다. 이 함수를 추가했다고 원격 처리가 중지됐다고 주장하지 않는다.
- 새 소비자 등록 때 어떤 과거 요청을 처리해야 하는지, 실제 수신 대상 범위는 공동 검수에서 확정한다. 현재 발행 함수와 같게 등록 소비자별 모든 삭제 원장을 확인한다.
- 실제 DEV 다중 연결·큰 원장 성능·원격 삭제·모델·백업 검수는 미실시다. 단일 PGlite 시험은 대체 증거가 아니다.

## 반영과 복구

선행 outbox/receipt SQL 이후 적용할 별도 migration이다. 초기 데이터·cron·설정 변경이 없다. 실제 DB 적용은 별도 승인 후 한다. 문제 시 호출을 중지하며 원장과 기한을 보존한다. 삭제·기한 연장으로 되돌리지 않는다.
