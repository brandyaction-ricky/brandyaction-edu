# DEV 고정 QA 데이터와 Toss E2E 검수 기준

## 목적과 안전 경계

운영 데이터의 사본을 만들지 않고도 주문·결제·웹훅·수강권 흐름을 반복 검증한다. 이 문서의 데이터와 결제는 `brandyaction-edu-dev` Vercel 프로젝트, `brandyaction-edu-dev` Supabase 프로젝트, Toss 테스트 키에서만 사용한다.

다음 조건 중 하나라도 맞지 않으면 쓰기 검증을 시작하지 않는다.

- `GET /api/health`가 HTTP 200과 `ok: true`를 반환한다.
- `environment`가 `development`이다.
- `services.supabase.projectRef`가 DEV 프로젝트 참조와 일치하고 `reachable`이 `true`다.
- `services.toss.mode`가 `test`이고 client, secret, webhook 설정이 모두 `true`다.
- 브라우저 주소가 `https://brandyaction-edu-dev.vercel.app` 또는 승인된 해당 브랜치 Preview다.

상품 저장 시 생성되는 기본 기수는 `[DEV QA] Toss E2E 기본 기수`로 관리한다. 실제 판매 상품과 혼동하지 않도록 모든 QA 전용 레코드 이름은 `[DEV QA]`로 시작한다.

### QA 구매자

- 개인 운영 계정 대신 DEV 전용 구매자 계정 1개를 사용한다.
- 이메일과 비밀번호는 저장소·문서·로그에 기록하지 않는다.
- 관리자 권한을 부여하지 않는다.
- 반복 실행 시 같은 구매자를 쓰되 주문은 매번 새로 생성한다.

### 실행 식별자

- 실행 ID: `QA-YYYYMMDD-HHMM-KST`
- 주문 메모나 운영 기록에 실행 ID를 남겨 한 번의 브라우저 흐름, Toss 거래, DB 상태와 관리자 화면을 연결한다.
- 결제 키, 웹훅 토큰, 서비스 역할 키는 증거 문서에 남기지 않는다.

## 필수 E2E 시나리오

### E2E-01 카드 결제 성공

1. QA 구매자로 로그인한다.
2. 고정 QA 상품 상세에서 신청하고 1,000원 주문을 만든다.
3. Toss 테스트 결제를 완료한다.
4. 성공 페이지가 주문 번호와 완료 상태를 표시하는지 확인한다.
5. 관리자 주문 화면에서 주문·결제·수강권을 확인한다.
6. Vercel 로그에서 결제 승인 API와 웹훅이 오류 없이 끝났는지 확인한다.

통과 조건:

- 주문 상태 `paid`
- 결제 상태 `approved` 또는 현재 스키마의 동등한 완료 상태
- 승인 금액 1,000원, 통화 KRW
- 수강권이 QA 구매자에게 1건만 발급됨
- 동일 결제 승인·웹훅 재처리 후 중복 결제나 중복 수강권이 생기지 않음

### E2E-02 웹훅 재시도 멱등성

동일 Toss transmission 또는 동일 결제 상태 이벤트가 다시 도착했을 때 `payment_events`에는 식별 가능한 기록이 남고, 주문·결제·수강권 결과는 한 번만 반영되어야 한다.

### E2E-03 가상계좌 상태 전이

테스트 가상계좌 발급 후 `WAITING_FOR_DEPOSIT` 상태가 저장되고, 테스트 입금 콜백 이후 결제 완료와 수강권 발급이 한 번만 일어나야 한다. Toss 테스트 환경에서 입금 콜백 재현 수단이 확인되지 않으면 미수행 사유를 기록한다.

### E2E-04 취소·부분 취소

별도 환불 승인과 `EDU_ALLOW_LIVE_REFUNDS` 안전장치 확인 후에만 수행한다. 기본 QA에서는 실행하지 않고, 승인 전까지 코드 테스트 결과만 증거로 사용한다.

## 증거 기록

각 실행은 다음 항목을 남긴다.

| 경계 | 증거 |
| --- | --- |
| 브라우저 | 상품명·금액·성공 화면, 콘솔 오류 유무 |
| 주문 API | 요청 시각, HTTP 상태, 비밀값을 제거한 오류 요약 |
| Toss | 테스트 모드 표시, 거래 상태, 금액 |
| 웹훅 | 이벤트 유형, HTTP 상태, 재시도 여부 |
| DEV DB | 주문·결제·이벤트·수강권의 ID와 상태 |
| 관리자 UI | 동일 주문의 상태와 금액 표시 |
| 배포 | 배포 URL, Git 커밋, `/api/health` 결과 |

## 유지·정리 원칙

- seed, reset, 운영 데이터 복사로 고정 데이터를 만들지 않는다.
- 결제 이력이 연결된 QA 주문은 임의 삭제하지 않는다.
- QA 상품은 장기 재사용하며 변경이 필요하면 실행 기록에 변경 전후를 남긴다.
- QA 데이터는 통계·운영 집계에서 `[DEV QA]` 접두어 또는 전용 구매자로 제외한다.
- 운영 DB, 운영 Toss 키, 운영 웹훅에는 이 시나리오를 실행하지 않는다.
